# Issue #72 [ApiTests][T15] — `tests/contacts/crud-lifecycle.spec.ts` (сквозной CRUD)

> **Режим:** test-authoring (метки `api`, `testing`). Всё поведение уже реализовано —
> продакшн-код не трогаем. Единственный артефакт: новый spec-файл с E2E-тестами Playwright.

## Требование

Единый сквозной интеграционный сценарий жизненного цикла контакта, проходящий все пять
эндпоинтов в одном потоке:
`create` → `getById` (проверка) → `update` → `getById` (проверка изменений) → `delete` →
`getById` (`404`). На каждом шаге проверяются статус и данные; данные self-contained;
очистка гарантирована даже при падении на любом шаге.

## Критерии приёмки

| # | Критерий |
|---|----------|
| A1 | Единый поток без зависимости от seed (контакт создаётся в тесте). |
| A2 | `create` → `201`, id извлечён из `Location`. |
| A3 | `getById` после create → `200`, данные совпадают с отправленными (схема + значения). |
| A4 | `update` → `204`; последующий `getById` → `200` и показывает **новые** значения. |
| A5 | `delete` → `204`; последующий `getById` → `404`. |
| A6 | Каждый шаг проверяет и статус, и данные (не только код ответа). |
| A7 | Гарантированная очистка при падении на любом шаге (фикстура авто-удаляет; повторный `DELETE` в teardown безопасно проглатывает `404`). |
| A8 | (Доп.) промежуточная проверка видимости через `list(search)` в пределах жизненного цикла — по токену находится, после delete — не находится. |

## Факты об API (основание для дизайна)

- `POST api/Contacts` → `201`, **тело пустое**, id только в заголовке `Location`.
- `GET api/Contacts/{id:int}` → `200` `ContactModel { id, firstName, lastName, birthday }` | `404`.
- `PUT api/Contacts/{id:int}` → `204` (полная замена; id маршрута перекрывает тело) | `400` | `404`.
- `DELETE api/Contacts/{id:int}` → `204` | `404`.
- `GET api/Contacts?search=` → `200` `{ totalRows, rows[] }`; поиск по first/last name.

## Tests — сценарии Playwright (`crud-lifecycle.spec.ts`)

**`Contact CRUD lifecycle` — один тест, последовательный поток (A1–A8)**
1. **create** валидным контактом (с уникальным токеном в имени) → `201`, `id > 0` (A2).
2. **getById** → `200`; схема валидна; `firstName`/`lastName`/`birthday` совпадают с
   отправленными (A3, A6).
3. **list(token)** → `200`; созданный контакт присутствует по токену (A8, промежуточно).
4. **update** новым валидным телом (другие firstName/lastName/birthday) → `204` (A4).
5. **getById** → `200`; схема валидна; значения соответствуют **обновлённым** (A4, A6).
6. **delete** → `204` (A5).
7. **getById** → `404` (A5, A6).
8. **list(token)** → удалённый контакт больше не находится по исходному токену (A8).

Тест один и намеренно линейный: это интеграционная проверка непрерывного жизненного цикла,
а не набор изолированных кейсов (последние уже покрыты в `create/get-by-id/update/delete` спеках).

## Изоляция и очистка

- Контакт создаётся в тесте через `contactsClient.create`; фикстура регистрирует id и удаляет
  его в teardown — **очистка выполнится, даже если тест упадёт на любом шаге** (A7).
- Уникальность обеспечивает токен (`newTestToken`), тест устойчив к параллельному прогону на
  общей БД и не зависит от seed.
